# Искенди — табло заказов

Веб-табло готовности заказов для дюрюмной «Искенди». Заказы подтягиваются из
кассы **iiko** и появляются на табло; касса двигает их по статусам, а гость с
телефона (или с телевизора в зале) видит, готов ли его номер. Снимает толпу у
окна в пик.

Проект **отдельный** от аналитического дашборда `iskendy_analytic`: другая
аудитория (гость с улицы, а не владелец), другой жизненный цикл, отдельный
деплой (но данные о заказах табло берёт из iiko через ручку аналитики).

## Модель

- Статус ведётся **на уровне заказа**: `open` (открытый — приехал из iiko, ещё
  не взяли в работу) → `preparing` (готовится) → `ready` (готово) → `served`
  (выдано). «served» снимает заказ с табло, но остаётся в истории.
- **Источник заказов — iiko** (Фаза 1, поллинг): фоновый `iiko_poller` раз в
  ~30 сек дёргает ручку аналитики (`/api/orders/today`) и заводит новые заказы
  как «открытые» (окно свежести — последние 20 мин, дедуп по номеру за день).
  Ручной ввод номера на кассе остаётся как fallback (создаёт сразу «готовится»).
  Оба пути дедуплицируют по номеру за день **в любом статусе**: номер, который
  сегодня уже был, второй раз не заводится (раньше ручной ввод проверял только
  активные, и за месяц набежало 34 дубля «iiko + вручную»).
- По каждому заказу хранятся **времена этапов**: приём (`created_at`), готово
  (`ready_at`), выдано (`served_at`). Плюс **журнал событий** (`order_events`) —
  аудит всех переходов.
- **Ничего не удаляется физически.** Снятый кассиром заказ и «Новый день»
  проставляют `deleted_at`, статус остаётся тем, каким был в момент снятия, а в
  журнал идёт событие на каждый заказ — с номером. Все рабочие выборки (табло,
  история, аналитика, право на отзыв) фильтруют `deleted_at IS NULL`.
- Гость видит заказ с «Готовится» (статус «открытый» — внутренний, для кассы).
  Номер показывается такой же, как в iiko (напр. 5221).
- **Гость может подписаться на свой заказ** по номеру с чека — в том числе
  **до того, как заказ доехал из кассы**: из iiko номер приходит не мгновенно, и
  заставлять гостя ждать незачем. Экран показывает «Ждём кухню» и оживает сам;
  если через минуту заказа так и нет, честно пишет «Заказ не найден» и просит
  проверить номер — вместе с выдуманным номером и снятым кассиром заказом этот
  путь один (`MY_PENDING_HINT_MIN`). Телефон
  сам скажет, когда заказ готов (звук, вибрация, системное уведомление), а после
  выдачи попросит оценку. Оценка привязана к номеру заказа и фактическому
  времени ожидания — см. [docs/feedback-flow.md](docs/feedback-flow.md).

## Экраны (маршруты)

- `/` — лендинг-мультиссылка (главная). Занимает высоту экрана целиком тремя
  зонами: сверху логотип и слоган, по центру кнопка на табло, в футере —
  Яндекс.Карты, часы работы, соцсети и копирайт. На десктопе карты и часы встают
  в один ряд. Фоном идёт фирменный орнамент (шашка из розетки бренда и фески,
  рисуется в SVG прямо на странице — картинок в ассетах нет); тот же орнамент на
  `/board`, `/tv` и `/staff`, без него только `/stats`.
- `/board` — гостевое табло. Гость видит одно действие: поле для номера с чека.
  Подписка на свой заказ — единственный путь, потому что только она приводит к
  уведомлению и оценке. Общая очередь («Готовятся» / «Готово») с телефона
  **скрыта** (18.08.2026, решение владельца; раньше сворачивалась под кнопку).
  Разметка и логика очереди в коде остались — метки «ВРЕМЕННО СКРЫТО» и
  «ОЧЕРЕДЬ СКРЫТА» в `frontend/index.html` показывают, что снять для возврата.
- `/board?my=1` — личный экран заказа: свой номер крупно, путь по статусам,
  звёзды оценки и продолжение (карты для довольных, форма для недовольных).
- `/tv` — общая очередь крупно, для **телевизора в зале** (подогнан под 1366×768).
  С 18.08.2026 фирменный орнамент есть и здесь (раньше его убирали ради
  читаемости номеров издалека).
- `/staff` — касса: двигать статусы (цвета: 🔵 открытый · 🟠 готовится · 🟢
  готово), счётчики по статусам, журнал событий. Строка «Выдано сегодня: N»
  раскрывается в список выданных с кнопкой «Вернуть» — откат ошибочной выдачи. Заказы приезжают из iiko сами,
  плюс ручной ввод номера — запасной путь на планшете, если касса пробила мимо
  или поллер молчит.
- `/stats` — аналитика (под паролем кассы): выбор дней, KPI, графики по часам,
  **оценки гостей** (средняя, доля 5★, охват, связка «ожидание ↔ оценка», топ
  тегов) и **путь каждого заказа** — строка раскрывается в карточку с лентой
  переходов по статусам и отзывом целиком.

Один статичный `index.html` обслуживает все экраны — выбор по URL.

## Стек

- **Backend:** FastAPI + SQLite (stdlib `sqlite3`), JWT-авторизация кассы на
  `hmac`. Фоновые задачи: iiko-поллер, ночной бэкап. Заказы из iiko — через httpx.
  Зависимости фиксирует `poetry.lock`; в контейнере приложение работает под
  непривилегированным пользователем `app`.
- **Frontend:** один статичный `index.html` без сборки (палитра «Bakır» / бренд-
  градиент, инлайн-SVG графики без внешних библиотек). Опрос статуса раз в 5 сек.

## Данные и бэкап

- Всё в SQLite `iskendy.db` (в проде — Docker volume `app-data` → `/data`).
  Таблицы: `orders`, `order_events`, `feedbacks` (отзывы гостей: оценка, теги,
  комментарий, контакт, фактическое ожидание; один заказ — один отзыв на уровне
  уникального индекса), `guest_events` (шаги гостя по воронке), `order_claims`
  (за каким телефоном закреплён номер заказа), `staff_session` (единственная
  активная сессия кассы) и `security_events` (журнал событий безопасности).
- **Миграции** — в `init_db()`: `PRAGMA table_info` + `ALTER TABLE`,
  идемпотентно, применяются при старте контейнера. Отдельного инструмента нет и
  не нужно: изменения почти всегда «добавить колонку». Единственное исключение —
  разовое удаление `batch_log` и `day_state`, оставшихся от снятой модели
  «партий»: к аналитике они отношения не имели и кодом не читались.
- ⚠️ `guest_events` хранит номер заказа, время шага и метку устройства — по ним
  гость определяется косвенно, а его визиты связываются между собой. IP и
  User-Agent не пишем. База с отзывами и воронкой — чувствительные данные,
  наружу отдавать незачем.
- **Ночной бэкап** (`backup.py`): раз в день в 03:00 снимает gzip-копию в
  `/data/backups/` с ротацией (последние 30). Скачать вручную — `GET
  /api/backup/latest`.
- **Выгрузка вне сервера**: в 03:30 крон запускает `/root/iskendy/backup-to-drive.sh`,
  и rclone отправляет копии на Google Диск владельца (папка «Искенди — бэкапы
  БД»). Копии в volume защищают от порчи данных и ошибочного сброса, но не от
  смерти диска — они лежат рядом с боевой базой. Используется `copy`, а не
  `sync`: локально хранятся 30 копий, и sync стирал бы на Диске всё, что старше.
  Две неудачные попытки подряд → сообщение в тему аварий.

## Запуск в Docker

БД живёт в volume `app-data`. Нужен заполненный `.env` в корне.

```bash
cp .env.example .env        # задать STAFF_PASSWORD (+ IIKO_ORDERS_URL/TOKEN для iiko)
docker compose up -d --build
```

- Лендинг: http://localhost:8080/ · табло: `/board` · ТВ: `/tv` · касса: `/staff`
  · аналитика: `/stats`.

## Запуск локально без Docker

Запускать **из корня проекта** — там лежит `.env`, а настройки читаются
относительно рабочей директории (`env_file=".env"` в `backend/config.py`).
Если запустить из `backend/`, файл не найдётся: ссылки на отзывы окажутся
пустыми (кнопки не отрисуются), Telegram промолчит, пароль придётся передавать
руками. В Docker этой ловушки нет — там `.env` подставляет compose.

Зависимости ставит **poetry** по `poetry.lock` — версии зафиксированы, чтобы
локально и в проде работал один и тот же набор. `requirements.txt` больше нет.

```bash
poetry install --only main --no-root
poetry run uvicorn main:app --app-dir backend --reload --port 8080
```

⚠️ `.env.prod` — снятая копия боевого файла, лежит локально для восстановления
после смерти сервера. Запускать с ней **нельзя**: уйдут настоящие уведомления в
рабочий чат и откроется доступ к боевой кассе. Для локальной работы — `.env` из
`.env.example`. В `.gitignore` игнорируется всё `.env.*`, кроме примера: раньше
правило ловило только `.env`, и `.env.prod` уехал бы в репозиторий.

Отдельная БД для опытов, чтобы не трогать рабочую, — через `DB_PATH`:

```bash
DB_PATH=/tmp/demo.db FEEDBACK_ALERT_ENABLED=false uvicorn main:app --app-dir backend --port 8080
```

## Отзывы гостей

Воронка целиком описана в [docs/feedback-flow.md](docs/feedback-flow.md), планы —
в [docs/feedback-next.md](docs/feedback-next.md). Коротко, как это работает:

1. Гость вводит номер с чека на `/board` → попадает на личный экран заказа.
   Тогда же браузер спрашивает разрешение на уведомления. Поле для номера —
   единственное действие на экране, общей очереди с телефона нет: без подписки
   не будет ни уведомления, ни оценки, поэтому она и есть весь путь.
2. Заказ становится готов → звук, вибрация и системное уведомление.
3. Через `FEEDBACK_PROMPT_DELAY_SEC` после выдачи карточка превращается в
   оценочную: пять звёзд, один тап.
4. **4–5★** — ссылки на Яндекс.Карты, 2ГИС и соцсети. **1–3★** — форма «что
   было не так» (теги, комментарий, контакт), наружу такой отзыв не уходит.
5. Каждый отзыв уходит в Telegram, в тему отзывов рабочего чата — обе ветки.
   Личных адресатов нет намеренно: система должна работать без владельца, а не
   через него. Негатив уходит всегда, поток хороших оценок гасится рубильником
   `FEEDBACK_NOTIFY_ALL`. Ошибка отправки не роняет отзыв.

Гость может переставить оценку (промах по звезде — обычное дело), пока не
отправил форму; окно правки — `FEEDBACK_EDIT_WINDOW_MIN`. Защита гостевых
ручек: заказ закрепляется за первым вбившим его телефоном и без выданного ключа
оценку не принять, один отзыв на заказ (уникальный индекс), отдельный ключ
правки в ответе на оценку, rate-limit по IP (раздельные корзины для чтения,
записи, шагов воронки, занятия номера и входа — в зале все телефоны выходят
через один адрес, поэтому лимиты не должны съедать друг друга).

## Безопасность

- **Отзыв может оставить только тот, кто следил за заказом.** Номер с чека
  совпадает с номером на телевизоре, то есть виден всему залу, и сам по себе
  никого не удостоверяет: раньше оценку за чужой заказ отправлял любой
  прохожий одним запросом. Теперь номер закрепляется за телефоном, который
  вбил его первым (`POST /api/guest/claim` → ключ), и оценка принимается только
  с этим ключом. Гость подписывается сразу после оплаты, а оценить можно лишь
  после выдачи — между этим десяток минут готовки, так что настоящий гость
  успевает первым. Захват номеров впрок ограничен: не больше
  `CLAIM_MAX_PER_GUEST_DAY` на устройство за день, занятие номера, так и не
  появившегося в кассе, протухает через `CLAIM_PENDING_TTL_MIN`, а устройство,
  гребущее номера пачкой, попадает в алерт.
- **Касса открыта на одном устройстве.** Планшет стоит за столом залогиненным
  месяцами (пароль вводить неудобно, оттого и долгий токен), поэтому второй
  вход тем же паролем — сигнал об утечке, а не «хозяин зашёл с телефона». Такой
  вход отклоняется с 409 и уходит в алерт; планшет при этом не разлогинивается,
  чтобы смена не осталась без кассы посреди дня. Освободить кассу — кнопка
  «Выйти» (`POST /api/auth/logout`), она гасит сессию на сервере, а не только
  чистит `localStorage`.
- **Вход персонала** — не больше 10 попыток в минуту с адреса
  (`RATE_LIMIT_LOGIN`). Пароль один и открывает всё: кассу, аналитику, инбокс
  отзывов с контактами гостей и выгрузку базы, поэтому перебор закрыт.
- **X-Forwarded-For.** Caddy **дописывает** настоящий адрес в конец заголовка,
  сохраняя всё, что прислал клиент, — значит первый элемент сочиняет сам
  клиент. Берём последний, и только когда запрос пришёл из внутренней сети
  (`_trusted_peer`): при прямом обращении весь заголовок выдуман, и последний
  элемент не лучше первого. Uvicorn запускается с `--no-proxy-headers`, иначе
  он подменил бы `client.host` тем же заголовком и проверять было бы нечего.
  ⚠️ Раньше здесь бралcя первый элемент — любой лимит по IP, включая попытки
  пароля, обходился одной строкой в curl.
- **CSP** (`CSP` в `main.py`) — чужой скрипт не загрузится, а увести данные
  некуда: `connect-src` закрыт своим origin. Разрешены только `mc.yandex.ru`
  (Метрика), Google Fonts, `data:` (SVG орнамента и QR) и `blob:` (вебвизор).
  ⚠️ `'unsafe-inline'` обязателен, пока весь JS страницы инлайновый и
  обработчики висят в `onclick`: CSP ограничивает источники, но не код в
  разметке. Снять — только переписав фронт на внешние файлы.
- **SQL** везде параметризован; в текст запроса подставляется только число `?`
  (для `date IN (...)`) и имя колонки из жёсткого словаря в `set_status`.
- **Вывод данных гостя** (комментарии, теги, контакты) экранируется `esc()`;
  ссылка на Telegram собирается вручную и только на `t.me` — иначе владелец,
  разбирая жалобу, кликал бы по чужому адресу.
- **`/api/qr` кодирует только свои адреса.** Ручка открытая (QR табло рисуется
  гостям), а с произвольной строкой получался генератор QR на чужой сайт,
  отдаваемый с домена ресторана: готовая листовка «оплатите заказ» с честной
  проверкой источника.
- **Публичная проверка заказа не отдаёт `orderId`** — он сквозной по всей
  истории, и по его приросту считался бы оборот точки.
- **Журнал событий безопасности** — таблица `security_events` (время, вид,
  адрес, JSON с деталями). Пишутся восемь видов: вход удачный, неверный пароль,
  отклонённый вход, выход, упёршийся лимит, номер уже занят, исчерпан дневной
  лимит номеров, оценка за незанятый заказ. Живёт в основной БД намеренно — она
  уже уезжает на Google Диск, значит история попадает за пределы сервера
  бесплатно. Смотреть: `GET /api/security/events` и `/api/security/summary`.
  Паролей, токенов и ключей в журнале нет.
- Токен бота приглушён в логах (`httpx` на WARNING), `.env` и база — вне git.

**Telegram в РФ блокируется**, поэтому запросы к Bot API идут через прокси
(`BOT_PROXY_URL`); пустой — ходим напрямую.

`frontend/sw.js` — service worker ровно под системные уведомления (на Android
иначе нельзя). Кэша в нём намеренно нет, чтобы табло обновлялось сразу после
деплоя.

## Ошибочная выдача

Кнопки в строках заказов стоят вплотную, и в час пик кассир попадает в соседнюю.
До 25.08.2026 это было необратимо: `set_status` ищет заказ только среди активных
и на выданный отвечает «активного заказа нет».

Цена ошибки не в данных, а в госте. Заказ исчезает с табло, и человек, который
отошёл от стойки, больше никак не узнает, что его еда готова: номера нет, а его
телефон через три минуты предложит оценить заказ, которого он не получал.

Теперь строка «Выдано сегодня: N» на `/staff` раскрывается в список выданных, у
каждого кнопка «Вернуть». Возврат ставит заказ обратно в «готово», и телефон
гостя звенит заново — для него это обычный переход в «готово», такой же, как
первый раз.

Что при этом происходит под капотом:

- **Отметка выдачи стирается.** Иначе заказ разом выдан и не выдан, а время
  «готово → выдано» посчитается от ошибочного нажатия.
- **Отметка готовности восстанавливается**, если её не было. Выдать, минуя
  «готово», можно только через API, но заказ, который выдали, точно был готов —
  без отметки он выпал бы из расчёта времён.
- **Возврат пишется в журнал** отдельным переходом `served → ready` с источником
  `revert`, чтобы в аудите было видно не только сам факт, но и что это откат.
- **Заказ с отзывом вернуть нельзя.** Оценить можно только выданный заказ: раз
  отзыв есть, гость его получил, и промахом это не было.
- **Телефон гостя снимает свою отметку выдачи**, когда видит номер снова на
  табло. Иначе при настоящей выдаче экран оценки выскочил бы мгновенно — отсчёт
  трёх минут шёл бы от ошибочного нажатия.

## Логи и самовосстановление

**Логи.** Строки о запросах пишет само приложение, а не uvicorn
(`--no-access-log`): только оно умеет достать настоящий адрес гостя. В строке
время, метод, путь, код, адрес и длительность. Опрос табло, health и статика не
пишутся — раньше они давали 92% объёма (109 278 строк из 119 231 за пять дней),
и полезное в этом шуме не находилось. Ошибки от них пишутся всегда, чтобы
отвалившийся `/api/status` не остался незамеченным.

`docker logs` живут ровно столько, сколько живёт контейнер: любой деплой
пересоздаёт его, и вся история исчезает. Поэтому приложение дублирует лог в
`/data/logs/app.log` внутри volume — шесть кусков по 5 МБ, это несколько
месяцев при потолке в 30 МБ. Плюс ротация json-file в compose (10 МБ × 3),
заданная в сервисе, а не в `daemon.json`: правка демона требует его
перезапуска, то есть рестарта всех контейнеров на машине, включая чужие стеки.

```bash
docker exec iskendy cat /data/logs/app.log | grep ОТЗЫВ
```

**Самовосстановление.** Владелец не должен быть частью системы, поэтому порядок
такой: сначала починить, потом сообщить, что сделано. Сторож
`/root/iskendy/guard.sh` работает по крону каждые 5 минут:

| Проверка | Что делает | Сообщение о развязке |
|---|---|---|
| Сайт не отвечает | ждёт 20 с, проверяет снова, перезапускает контейнер | сразу: «перезапущен, работает» |
| Перезапуск не помог | зовёт людей: «принимайте на бумаге» | «сайт снова отвечает» |
| Диск ≥ 88% | чистит образы и кэш сборки | «диск почищен, было X стало Y» |
| Очистка не помогла | зовёт людей | «с диском снова порядок» |
| Бэкап не уехал | повторяет через 5 минут, потом зовёт людей | «бэкап снова уезжает» |
| Поллер iiko молчит | «заносите вручную» | «ручной ввод больше не нужен» |

**У каждой тревоги есть развязка.** Тревога без сообщения о том, что всё
починилось, хуже отсутствия тревоги: в чате висит проблема, которой уже нет, и
следующее такое сообщение перестают принимать всерьёз. Отметка о проблеме
лежит в `/var/lib/iskendy-guard/`, поэтому одно и то же не повторяется каждые
пять минут, а снимается ровно один раз.

Здоровье проверяется по коду **200** через https с локального адреса. Первая
версия стучалась по http и считала успехом ответ Caddy 308 (редирект на https)
— проверка проходила даже при полностью остановленном контейнере.

Отдельно поллер iiko: пять неудачных тиков подряд (около двух с половиной
минут) → сообщение «заносите заказы вручную», при восстановлении → «ручной ввод
больше не нужен». Одиночный таймаут — обычное дело, по нему не пишем.

Повторы схлопываются: первое сообщение уходит сразу, дальше того же вида
копятся молча, и в конце десятиминутного окна прилетает строка «и ещё N таких».
Иначе перебор пароля залил бы тему сотней одинаковых строк, живой человек
замьютил бы её — и перестал видеть настоящие поломки.

**Куда что уходит.** Две темы рабочего чата: отзывы гостей отдельно, сбои и
безопасность отдельно. Адресаты заданы явно в `.env`
(`TELEGRAM_FEEDBACK_TARGETS`, `TELEGRAM_ALERT_TARGETS`, `TELEGRAM_DIGEST_TARGET`)
— раньше пустой `FEEDBACK_TARGETS` подставлялся по цепочке из digest, и правка
одного адреса утаскивала отзывы не туда.

## Воронка гостя (аналитика)

Шаги пишутся в `guest_events` — своя база, а не только Яндекс.Метрика: цели
Метрики не связать с временами готовки и не выгрузить рядом с ними. Восемь
шагов по порядку: `board_open` → `sub_try` → `sub_fail` / `sub_ok`
(+ `sub_pending`, если подписка обогнала заказ) → `ready_seen` → `rate_shown` →
`rated` → `review_click`.

Считаем **людей, а не клики**: у каждого визита случайная метка `session`
(живёт до закрытия вкладки), и повторный шаг в том же визите не пишется —
кроме `sub_try` и `sub_fail`, где важна каждая попытка. Номер заказа
прикладывается, если гость уже подписан; до подписки его нет.

**Постоянные гости** — по метке устройства `guest` (случайная строка в
`localStorage`, переживает визиты). Ответ `/api/stats/guest` содержит блок
`returning`: сколько всего гостей за период, сколько из них приходили раньше, и
разбивку «сколько разных дней приходил каждый» (1 / 2 / 3–5 / 6+).

Метка намеренно **не** выводится из IP или User-Agent: гостевой Wi-Fi и
мобильный NAT дают один адрес на весь зал (все слиплись бы в одного
«постоянного»), а десяток одинаковых айфонов — один и тот же UA. Своя метка и
точнее, и рассказывает о человеке меньше. Побочный эффект: гость, очистивший
браузер или пришедший с другого телефона, считается новым — долю постоянных
честно читать как «не меньше, чем».

`GET /api/stats/guest` отдаёт воронку (сколько визитов дошло до каждого шага и
доля от заходов) и разрез «дошли до оценки ↔ сколько ждали» по корзинам
до 5 / 5–10 / 10–15 / дольше 15 минут — им проверяется главная гипотеза:
теряем ли мы отзывы из-за долгого ожидания.

Экрана для этого пока нет — данные читаются ручкой. См. «Дальше».

## Тесты

```bash
poetry install --with dev --no-root
./scripts/install-hooks.sh    # один раз на машину: git-хук pre-push
poetry run pytest             # 74 теста, ~1.5 секунды
```

Подробности и грабли — в [backend/tests/README.md](backend/tests/README.md).
Покрыты восемь дыр, закрытых в августе 2026, плюс механика заказов, логи и
маршрутизация уведомлений. Тесты проверены мутациями: каждую дыру возвращали в
код и убеждались, что падает конкретный тест.

Запускаются автоматически на двух рубежах:

- **`pre-push`** — локальный git-хук, останавливает пуш со сломанными тестами.
  Обходится флагом `--no-verify` и живёт только на этой машине, поэтому это
  быстрая подстраховка, а не гарантия. Ставится `./scripts/install-hooks.sh`,
  сам хук — `scripts/pre-push` (в `.git/hooks` он симлинком, потому что каталог
  хуков не версионируется и после свежего clone пустой).
- **GitHub Actions** — `.github/workflows/tests.yml`, на каждый пуш в `main` и
  на каждый PR. Настоящий сторож: работает независимо от того, кто и откуда
  пушит. Важен потому, что деплой делает `git pull` из `main` — сломанный код,
  попавший в ветку, доехал бы до прода ближайшей ночью.

## Чего нет
- **Шесть ручек работают без экрана** — смотреть их можно только запросом:
  `/api/feedback/list`, `/api/feedback/status` (инбокс отзывов),
  `/api/security/events`, `/api/security/summary` (журнал безопасности),
  `/api/auth/session`, `/api/backup/list`. Данные копятся, но никто их не видит.
- **`TELEGRAM_DIGEST_TARGET` настроен, а сводки нет.** Адресат в `.env` задан,
  кода, который бы что-то слал вечером, не написано.
