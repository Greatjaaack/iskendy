# Новый фронт: план стабильного запуска в Docker

Как довести `iskendy-frontend` от «работает у автора на маке» до предсказуемой сборки на нашем сервере. Локальный стенд уже есть: `docker/` этого репо (ветка `local/docker`), см. `docker/README.md`.

## Исходные ограничения

| Ограничение | Следствие |
|---|---|
| Прод — `git pull && docker compose -f docker-compose.prod.yml up -d --build` в `/root/iskendy`, один контейнер `iskendy`, `mem_limit: 256m` | Новый фронт не должен добавлять рантайм-процесс: только статика внутри того же образа |
| Диск сервера занят на ~82 % | Нельзя тащить `node_modules` (~600 МБ) и браузеры Playwright на сервер при каждой сборке |
| Сборка фронта: Node 24.19 ровно (`engines`), `npm ci`, git для `VERSION` | Node в образе прода не нужен — только в builder-стадии или вообще вне сервера |
| Репозиторий фронта публичный, у чужого автора | Версию закреплять коммитом/архивом с sha256, а не `main` |
| На прод ничего мимо git (наше правило) | Версия фронта должна быть записана в нашем репо |

## Варианты

| | A. Архив релиза + `ADD --checksum` | B. git submodule + сборка в builder-стадии | C. Собранный `dist/` коммитом во `frontend/` |
|---|---|---|---|
| Что в нашем репо | URL и sha256 архива в `Dockerfile` | ссылка на коммит фронта | готовые файлы |
| Node на сервере | не нужен | нужен в builder (кэш слоёв ~600 МБ) | не нужен |
| Воспроизводимость | полная (sha256) | полная (коммит + lockfile) | полная |
| Зависимость от GitHub при деплое | да (скачать архив) | да (submodule) | нет |
| Откат | вернуть строку в `Dockerfile` | вернуть коммит submodule | `git revert` |
| Кто делает релиз | автор фронта публикует GitHub Release | мы | мы |

**Рекомендация — C на старте, A когда автор начнёт выпускать релизы.** C не требует ни Node, ни сети на сервере, деплой остаётся прежним `git pull`, сгенерированные файлы ревьюятся диффом `VERSION`/`ROUTES.json`. Сборку делает Docker-стенд локально (`--target dist`), архив проверяется sha256 тем же `assemble-release`.

## Шаги

| # | Шаг | Готово, когда |
|---|---|---|
| 1 | Скрипт `scripts/import-frontend.sh <коммит>` в табло: клонирует фронт на коммит, собирает `docker build --target dist`, кладёт `dist/` во `frontend/`, пишет `frontend/VERSION` | Две сборки одного коммита дают одинаковый sha256 архива |
| 2 | Проверка состава до коммита: `index.html`, `legacy.html`, `sw.js`, `app/`, `assets/`, `VERSION`, `ROUTES.json`; ни одного `.map` | Тест в `tests/` табло падает на лишний/пропавший файл |
| 3 | `legacy.html` сверять с прежним `frontend/index.html` (sha256 из `legacy/SOURCE.json`) | Правка кассы в табло без синхронизации фронта ломает сборку, а не прод |
| 4 | Бэкенд: `/tv`, `/staff`, `/stats` → `legacy.html` напрямую; `QUIET_PATHS` + `/app/`; `Cache-Control` для `/app/*` | Тесты `test_public_surface` обновлены |
| 5 | `healthcheck` в `docker-compose.prod.yml`: `GET /api/health` + наличие `frontend/index.html` и `frontend/app/` | `docker ps` показывает `healthy`; пустой фронт — `unhealthy`, а не «молчаливый сбой» |
| 6 | Смоук после деплоя (только чтение): `/`, `/board`, `/VERSION`, `/sw.js` — 200; `/tv` отдаёт legacy; на `/` нет noindex, на остальном есть | Скрипт `scripts/smoke-front.sh`, запускается из скилла `prod-server` |
| 7 | Откат одной командой: `git revert` коммита импорта + обычный деплой | Отрепетировано на локальном стенде |
| 8 | Переход на A, когда у автора появятся релизы: builder-стадия `FROM alpine` + `ADD --checksum=sha256:…`, `frontend/` перестаёт коммититься | Деплой без Node и без сгенерированных файлов в git |

## Стабильность контейнера

- Образ прода не меняется по составу: Python + статика, `mem_limit: 256m` хватает (статика не в памяти).
- Builder-стадии, если появятся, — только `--target dist`, не в прод-образе; кэш BuildKit чистить `docker builder prune --filter until=168h` в ночном обслуживании.
- Версии закреплены: `node:24.19.0-bookworm` по digest, `package-lock.json`, коммит фронта.
- Локальный стенд (`docker/compose.yml`) повторяет прод: тот же бэкенд, тот же порядок сборки — что прошло там, пройдёт на сервере.
