## Теперь подключено

- Entry сохраняет результат существующего subscription service через
  `guestOrderStorage.add`, сохраняя прошлые записи. Повторный QR выбирает
  оригинальную запись и не заменяет её новыми `rated:false`/пустым feedback.
- Журнал из первого checkpoint стал live. Старые guest/visit keys и формат
  `iskendi_my_order` остаются прежними. Новая additive session запись
  `iskendy_selected_order_v1` содержит только дату/номер выбранного заказа,
  без claim/edit tokens. Старый ключ — projection для rollback; другие вкладки
  не используют его для переключения уже выбранного заказа.
- Начало другого заказа/сброс текущего номера сначала сохраняет исходную
  legacy запись в журнал, затем снимает только selection. Старый заказ и
  подтверждённая оценка не удаляются. При неуспешной миграции исходник остаётся.
- Rating читает конкретную дату/номер через scoped binding. Прежняя проверка
  `subAt` и `advanceOrder` сохраняется: запись другого server date не отправляется
  в сегодняшнюю оценку. Старые API-контракты и механизмы uncertain create
  (fresh check, отсутствие выдуманного editToken/rating) сохранены.
- Scoped writer вычисляет delta относительно своего последнего read;
  устаревшая полная запись не стирает чужую новую оценку или статус.
- Ошибка durable write возвращает `storage` в rating flow, а не `saved`.
  Claim, который нельзя сохранить, не ведёт к rating POST. Failed create
  persistence требует свежей проверки перед повтором; failed finish/detail
  не переводит форму в «спасибо». Используется существующий generic error UI.
- Телеметрия читает выбранный заказ своей вкладки; пути/названия целей/формат
  payload и лимиты не менялись.
- Cross-tab storage listener читает только order keys. Новый claim старой
  вкладки добавляется без смены selection новой вкладки; поздняя projection
  не сбрасывает `rated`, `done` и известный feedback. Новые feedback/future
  поля, отсутствующие в коллекции, импортируются.

Это согласованное необходимое расширение хранения для задачи multiorder;
старый single-record формат ADR-012 не заменён массивом. Нет новых зависимостей,
backend изменений, production вызовов, push или deploy.

## Ограничения и следующий блок

- Backend не отдаёт публичный orderId/history; same-day reuse не имеет
  устойчивого публичного incarnation ID. Нет восстановления списка после
  очистки storage. Пять — backend limit per guest/day; локальная очистка
  карточки не освобождает quota.
- Дневной guard использует актуальный cached server status. Атомарной связи
  date с feedback/claim API нет: смена дня между status и POST требует
  отдельного сценария в следующем блоке, без обещания отсутствующего контракта.
- У старой legacy вкладки нет revision для feedback edit. Импорт новой
  подтверждённой оценки без потери при миграции покрыт; arbitrarily reordered
  conflicting edits уже существующего feedback старой/новой версии пока
  не объявляются гарантированно разрешёнными.
- Журнал растёт; compaction/deletion policy пока отсутствует. Quota — явная
  ошибка, а не обещание вечного durable хранения.

Следующий блок: owner всех актуальных записей с bounded feedback checks,
визуальный список/детали/pager по новым макетам на 1440/1024/768/390,
отдельные rating/thanks и сценарии 0/1/2/3/5.
Gate остаётся OPEN: JS budget, Phase 0/ADR-003, multiorder UI/visual acceptance.
