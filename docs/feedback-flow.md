# Отзывы гостей на табло (feedback-воронка)

Спецификация. **Статус: MVP реализован** (ветка `feature/feedback-flow`), в прод
не выкачен. Ниже — исходный замысел; то, что по ходу работы разошлось с ним,
собрано в разделе «Как получилось на самом деле» в конце.

## Зачем

Гость на `/board` уже привязан к своему заказу и видит момент, когда его выдали.
Это единственная точка, где отзыв можно связать с **номером заказа** и
**фактическим временем ожидания** — таких данных нет ни у одного QR-опросника.

Три задачи, которые решает воронка:

1. Перехватывать недовольство до того, как оно уедет на Яндекс.Карты.
2. Гнать довольных гостей на карты, в 2ГИС и в соцсети.
3. Копить оценки в связке с временем ожидания — чтобы видеть, на какой минуте
   гость перестаёт быть довольным.

## Решения, зафиксированные с владельцем

- **Маршрутизация негатива — жёсткая.** Ссылки на карты видит только гость с
  оценкой 4–5. Оценка 1–3 уходит во внутреннюю форму и наружу не попадает.
  Риски — см. раздел «Риски» ниже.
- **Плюшки на старте нет.** Промокоды и мотивация — фаза 3, если конверсия
  отклика окажется низкой.
- **Негатив отрабатывает владелец лично.** Алерт идёт ему в личку и дублируется
  в тему рабочего чата — чтобы смена видела проблему в моменте и могла
  среагировать, пока гость ещё рядом.

## Жизненный цикл отзыва

```
заказ served
   ↓ (пауза ~3 мин)
экран «Оцените заказ №5221»  ← один тап по звёздам
   ↓
 ┌──────────────┴──────────────┐
4–5★                          1–3★
 ↓                             ↓
экран «Спасибо»               экран «Что пошло не так»
· Яндекс.Карты                · теги в один тап
· 2ГИС                        · текст (необязательно)
· Telegram / VK               · контакт (телефон или @tg)
                               ↓
                              алерт в Telegram владельцу и старшему смены
```

## Экраны гостя

Всё живёт внутри `/board` на телефоне. На `/tv` ничего из этого не
показывается — телевизор остаётся чистым табло.

### Шаг 0. Привязка к заказу

Два пути попадания:

- **Основной.** Гость открыл `/board` по QR с телевизора и тапнул «это мой
  заказ» на своём номере. Номер лёг в `localStorage` (`iskendi_my_order`),
  страница опрашивает статус раз в 5 сек (уже существующий поллинг). Когда
  заказ уходит в `served` — через 3 минуты всплывает экран оценки.
- **Запасной.** Гость сканирует отдельный QR со стойки выдачи → `/board?rate=1`
  → его просят ввести номер заказа вручную.

Ввод номера проверяется на бэкенде: заказ есть за сегодня, статус `served`,
отзыва по нему ещё нет. Иначе — понятная ошибка (см. «Краевые случаи»).

### Шаг 1. Оценка

Один экран, один тап, ничего больше. Каждое лишнее поле здесь режет отклик.

> **Как вам заказ №5221?**
> ★ ★ ★ ★ ★
> _Ответ займёт 5 секунд_

Кнопки «отправить» нет — тап по звезде сразу отправляет оценку и переводит на
следующий экран. Так оценка сохраняется, даже если гость бросит форму дальше.

### Шаг 2а. Оценка 4–5

> **Спасибо! Нам это правда важно**
> Расскажите о нас — это две минуты, а для нас много значит.
>
> [ Отзыв на Яндекс.Картах ]
> [ Отзыв в 2ГИС ]
>
> Мы в Telegram — там анонсы и новые позиции
> [ Telegram ]      [ Instagram ]

Кнопки карт открываются в новой вкладке, чтобы не терять страницу табло. URL —
в `.env`, см. «Конфигурация».

Telegram — основная кнопка соцсетей. Instagram ставим второй и мельче: он в
России заблокирован, без VPN у большинства гостей не откроется. VK у точки
пока нет — если заведут, добавляется третьей кнопкой без изменений в коде.

### Шаг 2б. Оценка 1–3

> **Извините. Расскажите, что было не так?**
>
> Теги (мультивыбор, один тап):
> `долго ждали` · `остыло` · `не тот вкус` · `мало положили` ·
> `персонал` · `чисто/грязно` · `цена` · `другое`
>
> [ поле: Что случилось? — необязательно ]
>
> **Хотим извиниться лично и угостить вас.** Куда написать?
> [ поле: телефон или @телеграм ]
>
> [ Отправить ]

Формулировка на контакте — ключевая. Не «оставьте номер телефона», а обещание
конкретного действия. Контакт необязателен: отзыв уходит и без него.

### Шаг 3. Финал

> **Спасибо. Мы разберёмся сегодня же.**
> Если оставили контакт — свяжемся в течение дня.

## Данные

Новая таблица в том же `iskendy.db`, миграция в `init_db()` по образцу
`order_events`.

```sql
CREATE TABLE IF NOT EXISTS feedbacks (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    date          TEXT    NOT NULL,   -- день ресторана, как в orders
    order_id      INTEGER NOT NULL,   -- FK на orders.id
    number        INTEGER NOT NULL,   -- дублируем номер для удобства выборок
    rating        INTEGER NOT NULL,   -- 1..5
    tags          TEXT,               -- через запятую: 'долго,остыло'
    comment       TEXT,
    contact       TEXT,
    contact_type  TEXT,               -- 'phone' | 'telegram' | NULL
    wait_seconds  INTEGER,            -- served_at - created_at на момент отзыва
    status        TEXT NOT NULL DEFAULT 'new',  -- new|contacted|resolved|visited
    staff_note    TEXT,               -- что сделали по негативу
    created_at    TEXT    NOT NULL,
    updated_at    TEXT    NOT NULL,
    ua_hash       TEXT                -- хэш User-Agent + IP, антиспам
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_feedback_order ON feedbacks (order_id);
CREATE INDEX IF NOT EXISTS idx_feedback_date ON feedbacks (date, rating);
```

`wait_seconds` пишем **на момент создания отзыва**, а не считаем потом — чтобы
цифра не поехала, если заказ позже отредактируют.

Уникальный индекс по `order_id` даёт правило «один заказ — один отзыв» на
уровне базы, а не на уровне надежды.

## API

| Метод | Путь | Кто | Что |
|-------|------|-----|-----|
| GET | `/api/feedback/check?number=5221` | гость | Можно ли оценить этот заказ. Отдаёт `{ok, reason, order_id}` |
| POST | `/api/feedback` | гость | Создать отзыв: `{number, rating}` → `{feedback_id, branch}` |
| POST | `/api/feedback/detail` | гость | Дописать детали: `{feedback_id, tags, comment, contact}` |
| GET | `/api/feedback/list` | касса | Инбокс отзывов с фильтрами по дате и статусу |
| POST | `/api/feedback/status` | касса | Сменить статус и оставить `staff_note` |
| GET | `/api/stats/feedback` | касса | Агрегаты для `/stats` |

Разделение на `POST /api/feedback` и `/api/feedback/detail` — намеренное.
Оценка фиксируется первым же тапом, детали дописываются вторым запросом. Если
гость бросит форму на полпути, оценка уже в базе.

Гостевые ручки без авторизации, но с защитой:

- максимум 1 отзыв на `order_id` (уникальный индекс);
- rate-limit по IP: 10 запросов в минуту;
- `POST /api/feedback/detail` принимает только отзыв не старше 30 минут —
  чтобы `feedback_id` нельзя было перебирать задним числом.

## Алерт по негативу

Оценка ≤3 → мгновенное сообщение в Telegram. Скорость тут и есть весь смысл:
гость ещё в зале или в двух шагах от окна, его можно догнать. Через сутки это
уже просто грустная строчка в базе.

Два адресата сразу: **личка владельца** и **тема рабочего чата**. Владелец
отрабатывает и решает, что делать; смена видит проблему в моменте и может
догнать гостя у окна, пока тот не ушёл. Список получателей —
`TELEGRAM_ALERT_TARGETS`, формат `chat_id[:thread_id]` через запятую, так что
добавить или убрать адресата можно без правки кода.

### Вечерняя сводка в рабочий чат

Отдельно от алертов: раз в день в 23:00 короткий итог в тему рабочего чата
(`TELEGRAM_DIGEST_CHAT_ID` + `TELEGRAM_DIGEST_THREAD_ID`).

```
Искенди · 11 августа
Оценок: 23 из 140 заказов (16%)
Средняя: 4.6 · пятёрок: 78%
Негатив: 2 (оба отработаны)
Чаще всего хвалят: вкус, скорость
Чаще всего ругают: долго ждали
```

Смысл — командная обратная связь без разбора полётов: смена видит результат
своей работы цифрой. Персональные негативы туда не сыпем, они уходят владельцу
в личку. Вешаем на тот же ночной планировщик, где живёт `backup.py`.

Формат:

```
🔴 Оценка 2 · заказ №5221
Ждал: 14 мин
Теги: долго ждали, остыло
«Заказ ждал 15 минут, дюрюм принесли холодным»
Контакт: @arslan_t
→ /staff → Отзывы
```

Отправка через Bot API, конфиг в `.env`. Реализация — отдельным модулем
`notify.py`, чтобы потом переиспользовать под другие уведомления.

## Экран `/staff` → вкладка «Отзывы» (фаза 2)

Без этого экрана негатив будет теряться в чате. Инбокс со статусами:

- `новый` → `связались` → `отработан` → `гость пришёл`

В строке: время, номер заказа, оценка, время ожидания, теги, текст, контакт,
кнопка «позвонить/написать» и поле заметки. Фильтр «только новые» по умолчанию.
Красная плашка на вкладке, если есть необработанные негативы старше 2 часов.

## Аналитика на `/stats` (фаза 3)

Поверх существующего дашборда:

- средняя оценка и доля 5★ по дням, тем же графиком, что заказы по часам;
- оценка в разрезе часов — где проседает пик;
- **связка «время ожидания ↔ оценка»**: разложить отзывы по корзинам ожидания
  (до 5 мин, 5–8, 8–12, 12+) и показать среднюю оценку в каждой. Так находится
  порог, после которого гость начинает злиться. Это самая полезная цифра во
  всей затее;
- доля заказов с отзывом — метрика самой воронки.

## Краевые случаи

| Ситуация | Поведение |
|----------|-----------|
| Номер не найден за сегодня | «Не нашли такой заказ за сегодня. Проверьте номер на чеке» |
| Заказ ещё не `served` | «Заказ ещё готовится — оцените, когда заберёте» |
| По заказу уже есть отзыв | «Спасибо, отзыв по этому заказу уже принят» |
| Номер вчерашний | Не принимаем. Оценка задним числом бесполезна и ломает `wait_seconds` |
| Гость закрыл вкладку до оценки | Оценка не собрана. Ловим запасным QR со стойки |
| Гость поставил 5★ и ушёл, не нажав кнопки карт | Нормально, оценка уже в базе. Клик по картам считаем отдельной метрикой |
| Оценка 3 | Считаем негативом. Тройка в общепите — это «больше не приду» |
| Одна страница, несколько заказов подряд | `localStorage` хранит последний номер, старые отзывы не перезаписываются |

## Конфигурация (`.env`)

```
# Ссылки на формы отзывов
REVIEW_URL_YANDEX=https://yandex.ru/maps/org/iskendi/52119597703/reviews/
REVIEW_URL_2GIS=https://2gis.ru/moscow/firm/70000001105862390/tab/reviews
SOCIAL_URL_TELEGRAM=https://t.me/iskendy
SOCIAL_URL_INSTAGRAM=https://instagram.com/_iskendy_/

# Алерты по негативу
FEEDBACK_ALERT_ENABLED=true
TELEGRAM_BOT_TOKEN=           # @BotFather
TELEGRAM_ALERT_TARGETS=       # chat_id[:thread_id] через запятую: личка + тема чата
TELEGRAM_DIGEST_TARGET=       # куда вечернюю сводку
FEEDBACK_NEGATIVE_MAX=3       # оценка <= этой считается негативом
FEEDBACK_PROMPT_DELAY_SEC=180 # пауза после served до показа экрана оценки
```

Все ключи — через `config.py`, `os.getenv` по коду не растаскиваем. Реальные
значения лежат в `.env` (он в `.gitignore`), в `.env.example` — только пустые
заготовки. Токен бота в репозиторий не попадает.

**Ссылки на карты надо доперепроверить с телефона.** Обе ведут на вкладку
отзывов, а не сразу в форму написания — гостю придётся тапнуть «Оценить» ещё
раз. Если у площадок найдётся прямой диплинк в форму, подставить его: каждый
лишний тап здесь стоит процентов конверсии. Ссылка 2ГИС собрана как
`/firm/<id>/tab/reviews`, проверить, что открывается именно отзывы.

**Как получить `TELEGRAM_ALERT_CHAT_IDS`.** Бот умеет писать только в чат с
числовым идентификатором. Написать [@userinfobot](https://t.me/userinfobot)
любое сообщение — в ответ придёт свой ID. Токен бота-отправителя — у
@BotFather, либо взять существующего бота точки.

## Метрики успеха

Смотрим через 2 недели после запуска:

| Метрика | Ориентир |
|---------|----------|
| Доля заказов с оценкой | 15–25% — нормально для QR-опроса без плюшки |
| Доля 5★ | опорная цифра, дальше следим за динамикой |
| Конверсия 5★ → клик на карты | 20–30% |
| Доля негатива с контактом | 40%+ — если ниже, переписываем формулировку |
| Негатив, отработанный за 2 часа | 90% — это вопрос дисциплины, а не продукта |
| Рост отзывов на Яндекс.Картах за месяц | главный внешний результат |

## Риски

**Жёсткий гейтинг нарушает правила площадок.** И Яндекс, и 2ГИС запрещают
выборочно просить отзывы только у довольных гостей. Санкция — фильтрация
отзывов или пометка карточки, не блокировка. Решение принято сознательно.

Смягчить можно в любой момент, не переписывая логику: показать ссылки на карты
и негативу тоже, но **после** формы обратной связи и другим тоном («если
хотите — напишите и на картах, мы ответим публично»). По факту до этого места
доходит меньшинство недовольных, а формально придраться не к чему. Держим как
план Б, если карточка начнёт фильтроваться.

**Резкий всплеск однотипных отзывов** тоже триггерит фильтры площадок. Не
гнать на карты всех разом в первый день — воронка и так распределена во
времени естественно.

## Этапы

**MVP.** Таблица `feedbacks`, гостевые ручки, экраны оценки и обеих веток на
`/board`, ссылки на карты и соцсети, Telegram-алерт на негатив.

**Фаза 2.** Вкладка «Отзывы» в `/staff` со статусами отработки.

**Фаза 3.** Блок аналитики на `/stats`, в первую очередь связка «ожидание ↔
оценка». Промокоды — если конверсия отклика окажется ниже 15%.

## Порядок реализации MVP

Шаги независимы и проверяемы по одному. После каждого — работающее состояние,
ничего не ломающее табло.

1. **`config.py`** — новые поля настроек (ссылки, токен, адресаты, пороги).
   Парсер `chat_id[:thread_id]` для `TELEGRAM_ALERT_TARGETS`.
2. **`db.py`** — таблица `feedbacks` в `init_db()` рядом с `order_events`,
   функции `feedback_check`, `feedback_create`, `feedback_detail`,
   `feedback_list`, `feedback_set_status`. Таблицы `orders` и `order_events`
   не трогать.
3. **`notify.py`** — новый модуль, отправка в Telegram Bot API через `httpx`
   (он уже в зависимостях, используется в `iiko_poller`). Ошибка отправки
   логируется и не роняет запрос: отзыв важнее уведомления.
4. **`main.py`** — шесть ручек из раздела «API». Гостевые без `require_staff`,
   штабные — с ним, как остальные.
5. **`frontend/index.html`** — экраны оценки внутри `board-view`, только для
   мобильной вёрстки. `body.tv` не затрагивать: там сейчас живёт `fitTvBoard()`
   и подгонка под телевизор, её легко сломать.
6. **Смоук-тест** — создать заказ, провести до `served`, оценить на 5 и на 2,
   проверить оба алерта и запись в базе.

### Чего не делать

- Не менять схему `orders` и `order_events` — на них завязаны табло, касса и
  аналитика.
- Не трогать `body.tv` и `fitTvBoard()` во фронте.
- Не показывать формы отзыва на `/tv`: телевизор остаётся чистым табло.
- Не коммитить `.env` — там боевой токен бота.
- Не деплоить и не перезапускать прод: ресторан работает, выкатка по решению
  владельца и только после закрытия.

# Как получилось на самом деле

Раздел дописан после реализации. Сама спека выше не переписывалась — по ней
удобно видеть, что менялось и почему.

## Что оказалось шире спеки

**Подписка на заказ.** В спеке гость тапал свой номер на табло. По ходу решили
иначе: номер вводится с чека в поле на `/board`, и гость попадает на личный
экран заказа — свой номер крупно, путь по статусам, а после выдачи — звёзды.
Тап по чужому номеру на табло намеренно **не** открывает заказ: иначе гости
разглядывали бы, кто сколько ждёт, и сравнивали себя с соседями.

**Подписка вытеснила общую очередь (16.08.2026).** Гости смотрели на список
номеров и не подписывались, а без подписки нет ни уведомления, ни оценки —
воронка обрывалась в самом начале. Теперь на `/board` первым идёт поле для
номера, а колонки «Готовятся» / «Готово» свёрнуты под кнопку «Посмотреть общую
очередь»: путь остался, но перестал быть путём по умолчанию. Совсем убирать
список не стали — на iPhone уведомления не работают (см. ниже), и для этих
гостей очередь остаётся единственным рабочим способом следить за заказом.
На `/tv` очередь развёрнута всегда: там она и есть содержимое экрана.
Развороты считаются целями `queue_open` / `queue_close` — по ним и решать,
убирать ли список совсем.

**Уведомления на телефон.** Кроме звука и вибрации при готовности заказа гость
получает системное уведомление (нужен `frontend/sw.js` — на Android иначе
нельзя). Разрешение спрашивается в момент подписки, а не на входе.

**Никаких модальных окон.** Оценка и то, что после неё, живут прямо на экране
заказа: карточка в момент опроса превращается из трекера в оценочную. Гость
может переставить оценку, пока не отправил форму, — промах по звезде обычное
дело.

**Уведомления обо всех отзывах,** а не только о негативе (решение владельца):
позитив идёт в рабочий чат, негатив — ещё и в личку.

**Аналитика вместо «фазы 3».** Оценка, теги, комментарий и контакт видны прямо
в таблице пути заказов на `/stats`; строка раскрывается в карточку с лентой
переходов по статусам и отзывом целиком. Рядом — сводка и связка «ожидание ↔
оценка» по корзинам.

## Чем защита отличается от описанной

| В спеке | Как сделано |
|---------|-------------|
| Окно 30 мин на дописывание — защита от перебора `feedback_id` | Выдаём **ключ правки** в ответе на оценку: перебор бессмыслен. Окно стало настройкой `FEEDBACK_EDIT_WINDOW_MIN` (по умолчанию 2 часа) |
| Rate-limit 10 запросов/мин по IP | Разделён: 120/мин на чтение, 20/мин на запись. В зале все телефоны выходят через один адрес, общий лимит блокировал соседей |
| — | Оценку **нельзя менять после отправки формы**: иначе в базе оказывалась запись «5★ + теги „остыло"», противоречивая и для смены, и для аналитики |
| — | Повторная отправка формы **не шлёт второе уведомление** в Telegram |

## Что не сделано из спеки

- **Вкладка «Отзывы» в `/staff`** (фаза 2) — ручки готовы, экрана нет. Пока
  негатив живёт в чате, а статусы отработки никто не двигает.
- **Вечерняя сводка в 23:00** — не реализована.
- **Строка `→ /staff → Отзывы`** в формате алерта: добавится вместе с вкладкой.
- **Клик по картам как метрика** — Метрика на `/board` отключена сознательно,
  так что конверсия «5★ → карты» пока не измеряется. Решение — в
  [feedback-next.md](feedback-next.md).

## Инфраструктурное

**Telegram в РФ заблокирован**, с VPS Bot API напрямую не отвечает — запросы
идут через прокси (`BOT_PROXY_URL`). Токен бота больше не светится в логах:
`httpx` печатал полный URL, а токен зашит в путь.
