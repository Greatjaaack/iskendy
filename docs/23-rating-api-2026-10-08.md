## Реализовано

- Диалог подключён к create/rate/detail/claim только по явному действию гостя.
  Для технического просмотра: сохранённый issued order и `/board?my=1&rate=1`.
  Новых backend routes, storage keys или полей авторизации нет.
- Один fresh-check gate для Entry, served-check и rating: минимум 20 s между
  началами GET на один номер. Eligibility не кэшируется для разрешения потери POST.
- Нет автоматических повторов POST. Потерянный create уточняется свежим check;
  already подтверждает наличие отзыва, но не восстанавливает editToken или
  выбранную эмоцию. UI не изображает выдуманную сохранённую оценку.
- Claim сохраняется в исходном поле и вызывается лишь при отсутствии ключа;
  client/event не занимает общий bucket во время claimEnsure.
- Late response после отмены, смены дня/номера/заказа, rollback или записи другой
  вкладки не меняет storage. Двойное Next блокируется синхронно.
- Ветка берётся только из ответа сервера. Negative R2→R3→detail→R4;
  positive R2→detail(tags only)→R4, без негативного шага комментария.
  Positive без тегов завершает локальный flow без ложного detailSent.
- Memory draft сохраняется при Escape, закрытии и возврате. Причины другой ветки
  удаляются после успешной смены эмоции. Комментарий не попадает в storage,
  URL, события, Метрику или логи. Contact скрыт по Q07.
- detailSent/done ставятся только после успешного detail; ошибки остаются
  видимыми, возможен только явный повтор. Тексты ошибок — backend REASON_TEXT
  и legacy fbFail, без новых придуманных формулировок.
- HTTPS review link проверяется существующим safeMapsHref; credentials и
  неподдерживаемые схемы скрыты. Используются прежние event/goal names.
- Добавлена реальная check-фикстура для синтетического заказа 997: capture
  выполнен внутри отдельного read-only Docker с `--network none`, без lifespan,
  production данных или изменений backend. Всего 34 captured responses.
