## Ограничение повторной покупки — справка для альтернативного макета

Новые решения переключения одиночного заказа приостановлены по сообщению
владельца; многозаказность, storage и API не внедрялись.
`src/storage/keys.ts`: localStorage `iskendi_my_order` содержит один объект
OrderRecord, не массив. Идентификатор гостя `iskendy_guest` остаётся общим,
`iskendy_visit` хранится в sessionStorage. Dock читает только текущий номер
и ведёт в `/board?my=1`; история покупок в гостевом frontend отсутствует.

Открытие QR-ссылки само по себе claim не отправляет. При ссылке на `/`
показывается Entry; сохранённый заказ остаётся до явного действия.
Фактический URL конкретного пользовательского QR пока не проверен.
Entry.submit вызывает createSubscriptionService и на успешном результате
полностью заменяет запись writeOrder(result.record), затем открывает my=1.
Второй номер не добавляется к первому, прежний объект не архивируется.

Сервис проверяет номер и дату board. Если номер уже выдан/оценён, feedback/check
может вернуть успешную локальную запись без нового claim. Иначе отправляется
POST /api/guest/claim с `{number, guest}`. Network/timeout допускают локальную
подписку с пустым claim: она тоже заменяет предыдущую запись, а ключ можно
получить перед оценкой (это делает сервис оценки `src/domain/rating/service.ts`). Business rejection и остальные API
ошибки не вызывают writeOrder и сохраняют старую запись. Двойное нажатие
во время запроса блокируется; уход со страницы отменяет поздний результат.
Кнопка «Другой заказ»/«Не мой номер» сначала явно forgetOrder, затем ведёт в `/`.
Не заявляется, что сервер запрещает несколько claim: этот вывод не следует
из клиентского singleton storage. Альтернативный макет списка потребует
отдельно согласовать хранение, жизненный цикл, сигналы и контракт поведения.
