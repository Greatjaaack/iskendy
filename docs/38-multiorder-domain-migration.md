## Проверенный контракт

Reference backend: `/tmp/iskendy-backend-166f35d-reference-20261008`,
commit `166f35d63366a0da6551158fee4f2ba9760473c5`, только чтение.

- Claim уникален по `date + number`, лимит — **5 закреплений на гостя за день**.
  Удаление локальной карточки не освобождает backend quota. Локальное число
  карточек не заменяет бизнес-ответ `too_many`.
- Claim возвращает `number` и `claimToken`, **не дату и не orderId**.
  Дату берём из свежего серверного status, не из локального календаря.
- `_can_rate` имеет внутренний orderId, но HTTP handler `feedback_check`
  явно удаляет его из публичного ответа (`backend/main.py:701–713`).
  Выдуманного API orderId нет. Локальная идентичность — дата и номер.
- Feedback check/create работают для сегодняшней даты backend. Сохранённую
  запись другого дня нельзя проверять/оценивать как сегодняшнюю по одному номеру.
- При переиспользовании номера **в тот же день** feedback выбирает последний
  неудалённый order; публичный API не даёт идентификатор такой инкарнации.
  Без изменения backend невозможно обещать распознавание всех переиспользований.
- Нет API списка всех claim гостя. После очистки storage весь список по guest ID
  восстановить невозможно; claimToken/editToken не должны попадать в URL/логи.

## Реализовано

`src/domain/orderCollection.ts`: версия коллекции, чистая миграция legacy,
валидация, идемпотентное добавление, патч по дате/номеру, фильтрация по
серверному дню и расчёт позиции/соседей без циклического перехода.
Сохраняются порядок, неизвестные поля записи и feedback. Повторный QR
не сбрасывает оценку. Изменение чужого статуса не меняет выбор.

`src/storage/orderCollectionStorage.ts`: **отдельный, пока не подключённый
к приложению** журнал `iskendy_orders_v1:<opaque operation key>`.
Каждая операция add/patch записывается в собственный ключ. Параллельные
операции двух вкладок не перезаписывают весь массив или всю запись.
Порядок операций — логический sequence, затем непрозрачный ключ при
одновременной записи; он не зависит от перевода системных часов.
Выбор экрана остаётся отдельным состоянием вкладки.

Миграция не удаляет и не переписывает `iskendi_my_order`. До успешной
записи исходные байты остаются доступны; quota/access error возвращается
явно, оценка не считается сохранённой. Невалидный журнал не заменяется
одной legacy-записью. После миграции журнал авторитетен: поздняя старая
legacy projection не перезаписывает коллекцию.

Это расширение подготовлено для новой задачи нескольких заказов; старый
storage API/формат и все потребители 0/1 пока работают прежним способом.
ADR-012 не объявляется задним числом изменённым. Подключение требует
документированного перехода: legacy projection, смешанные старые/новые
вкладки, закрытие/отказ от заказа и обслуживание растущего журнала.
В этом блоке нет удаления/компактации журнала и обещания бессрочного хранения.
