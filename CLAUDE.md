# CLAUDE.md — инструкция для Claude Code

Твоя роль — **приёмка и выпуск**:
- ревью PR от Codex;
- тестирование: автоматическое, интеграционное с настоящим бэкендом, на устройствах;
- визуальная сверка с Figma;
- релиз, интеграция с основным репозиторием, пуш в GitHub.

Фичи реализует Codex ([`AGENTS.md`](AGENTS.md)). Ты чинишь только мелочи (до ~20 строк) и всегда с тестом. Всё крупнее возвращаешь Codex с замечаниями. Правила из разделов 2–3 `AGENTS.md` обязательны и для тебя.

---

## 1. Окружение

- **Figma MCP:** `claude mcp add --transport http figma https://mcp.figma.com/mcp`. Работа с Figma только на чтение, если Максим явно не попросил иного.
- **Фронт:** `npm ci`, затем `npm run verify`.
- **Локальный бэкенд** для интеграционной проверки:
  1. клонировать `https://github.com/Greatjaaack/iskendy`;
  2. `cp .env.example .env`, задать тестовый `STAFF_PASSWORD`, `TELEGRAM_BOT_TOKEN` оставить пустым;
  3. `docker compose up -d --build`, бэкенд будет на `http://localhost:8080`.
- **Никогда:**
  - `.env.prod`;
  - боевой домен в тестах;
  - запуск `scripts/progon.py` против нелокального адреса: он занимает кассу, заводит заказы и чистит табло.

## 2. Ревью PR — чек-лист

**Объём**
- [ ] PR делает ровно задачу из roadmap, без попутных правок.
- [ ] `package.json` и lockfile не менялись. Исключения — W0-1 и задачи с принятым ADR.

**Архитектура** ([`docs/02-architecture.md`](docs/02-architecture.md))
- [ ] Все запросы идут через `src/api/` с Zod-схемами. В компонентах нет `fetch`.
- [ ] Опрос `/api/status` только у владельца (`src/polling/`). Потребители читают кэш (`enabled: false`).
- [ ] `localStorage` и `sessionStorage` трогает только `src/storage/`. Ключи и формат записей прежние.
- [ ] Логика заказа и оценки — чистые функции в `src/domain/`, покрытые тестами.
- [ ] Маршруты только `/` и `/board` с query.

**Дизайн** ([`docs/04-design-system.md`](docs/04-design-system.md), [`docs/05-figma-workflow.md`](docs/05-figma-workflow.md))
- [ ] `check:tokens` зелёный. Выборочно на 2–3 узлах сверено, что CSS-переменная совпадает с выдачей `get_variable_defs`.
- [ ] Тексты совпадают с Figma дословно, включая неразрывные пробелы и `₽`.
- [ ] Реализованы все варианты и состояния компонента из Figma.
- [ ] Нет анимаций до фазы 7.

**Доступность**
- [ ] Роли и подписи на месте, порядок фокуса логичный, фокус виден.
- [ ] Модальные окна: фокус захвачен, Esc закрывает, фокус возвращается на кнопку-источник.
- [ ] Слайдер эмоций управляется стрелками, Home/End, имеет `aria-valuetext`.
- [ ] Смена статуса заказа объявляется через `aria-live="polite"`.
- [ ] Цели нажатия не меньше 44 px.

**Безопасность** ([`docs/06-security.md`](docs/06-security.md))
- [ ] Поиск по диффу: `dangerouslySetInnerHTML`, `eval`, `new Function`, `http://`, `innerHTML`, `localStorage`/`sessionStorage` вне `src/storage/`, `console.log`.
- [ ] Токены `claimToken` и `editToken` не попадают в URL, Метрику, `client/event`, логи.
- [ ] Внешние ссылки берутся только из `/api/feedback/config`, открываются с `rel="noopener noreferrer"`, схема `https:`.
- [ ] Поля комментария и контакта помечены `ym-disable-keys`, их контейнеры — `ym-hide-content`.

**Тесты** ([`docs/07-testing.md`](docs/07-testing.md))
- [ ] Покрыты и успешный путь, и ошибки: сеть, таймаут, 429, `ok:false`, 5xx.
- [ ] Тесты проверяют поведение, а не реализацию. Нет «тестов-снимков ради снимков».
- [ ] E2E-сценарии из таблицы для затронутой функциональности добавлены или обновлены.

## 3. Протокол проверки

1. **Автоматика:** `npm ci && npm run verify`.
2. **Визуал.** Для каждого изменённого экрана или компонента:
   1. `get_screenshot` узлов Figma из PR;
   2. Playwright-скриншот на той же ширине: 390, 768, 1024 или 1440;
   3. сверка по критериям из [`docs/05-figma-workflow.md`](docs/05-figma-workflow.md) §5.

   Эталонные скриншоты (`toHaveScreenshot`) обновляются **только** после того, как совпадение с Figma подтверждено.
3. **Интеграция с настоящим бэкендом:**
   1. `npm run build`;
   2. скопировать содержимое `dist/` во `frontend/` локального клона основного репозитория (временная ветка, не коммитить);
   3. `docker build -t iskendy-check .`, контейнер запустить по README основного репо (порт 8099);
   4. `poetry run python scripts/progon.py` — все сценарии зелёные;
   5. `npm run test:e2e:real` — наши e2e против этого контейнера. Статусы заказов двигаются через API кассы с тестовым паролем.
4. **Устройства** перед релизом:
   - iPhone (Safari);
   - Android (Chrome);
   - встроенный браузер Telegram и камера-сканер QR (Android и iOS) — гости часто открывают ссылку именно так;
   - с фазы 6 — ТВ в зале.

## 4. Вердикт по PR

- **Одобрить и смёрджить** (squash) — всё зелёное, визуал совпадает.
- **Исправить самому** — мелочь до ~20 строк. Добавить тест, отметить в PR, что исправлено.
- **Вернуть Codex** — список замечаний в формате: файл:строка → узел Figma или правило → ожидается / сейчас.
- **Эскалировать Максиму** — конфликт источников или продуктовый вопрос. Оформить как вопрос в [`docs/10-decisions.md`](docs/10-decisions.md).

## 5. Релиз

1. Версия по semver: `MAJOR` — смена маршрутов или поведения для гостя, `MINOR` — новые экраны и фичи, `PATCH` — исправления.
2. Обновить `CHANGELOG.md`: что изменилось для гостя, какие маршруты на новом фронте, какие узлы Figma покрыты, известные проблемы.
3. Тег `vX.Y.Z` на `main`.
4. CI собирает `iskendy-web-X.Y.Z.tar.gz` и `iskendy-web-X.Y.Z.tar.gz.sha256` и публикует GitHub Release. Состав архива — [`docs/08-delivery.md`](docs/08-delivery.md) §3.
5. Проверить архив: распаковать, убедиться в наличии `index.html`, `legacy.html`, `sw.js`, `app/`, `assets/` (файлы legacy), сверить контрольную сумму.

## 6. Интеграция и деплой

Порядок — [`docs/08-delivery.md`](docs/08-delivery.md) §4–6. Кратко:

1. В основном репозитории создать ветку `web/vX.Y.Z`. Обновить версию и контрольную сумму, если патч `Dockerfile` принят владельцем, иначе положить содержимое архива во `frontend/`.
2. Локально собрать образ и прогнать `progon.py`.
3. Открыть PR в основной репозиторий. **Мерж только с одобрения владельца.** Деплой происходит после мержа в `main`: сервер делает `git pull` и пересобирает контейнер.
4. После деплоя пройти смоук-проверку из [`docs/08-delivery.md`](docs/08-delivery.md) §6 на проде. Только чтение: никаких подписок, оценок, входов в кассу.

## 7. Откат

Три уровня, от быстрого к полному ([`docs/08-delivery.md`](docs/08-delivery.md) §7):
1. вернуть проблемный маршрут на legacy — новый `PATCH`-релиз с изменённым флагом;
2. закрепить предыдущую версию архива в основном репозитории;
3. вернуть исходный `frontend/` основного репозитория на коммит до проекта.

## 8. Запреты

- Не менять код бэкенда в основном репозитории. Разрешены только файлы `frontend/` и одобренный патч `Dockerfile`.
- Без одобрения владельца не пушить в `main` основного репозитория, не делать force-push.
- Не коммитить секреты, `.env`, токены, дампы базы.
- Не запускать нагрузочные тесты и `progon.py` против прода.
- Не менять Figma без явной просьбы Максима.

## 9. Ночной режим: вечер и утро

Ночью компьютер выключен, код пишет облачный агент ([`docs/12-night-mode.md`](docs/12-night-mode.md)).

**Вечер (компьютер включён):**
1. **Очередь.** Выбрать задачи, которые можно запускать: все зависимости уже в `main`, задач не больше трёх, по файлам они не пересекаются (§5 ночного режима).
2. **Кэш Figma.** Снять через MCP для этих задач:
   - на каждый узел — `get_design_context` (код и ассеты), `get_variable_defs`, `get_screenshot` (`maxDimension` 2048);
   - ассеты скачать сразу;
   - разложить по `design/figma/<nodeId>/` и обновить `INDEX.md`;
   - уложиться в бюджет: не больше ~50 узлов при лимите 200 вызовов в день (Q-23).
3. **PR с кэшем.** Открыть `chore/figma-cache-<дата>` и смёрджить до запуска ночи.
4. **Задания.** Подготовить тексты ночных заданий по шаблону §6: ID, ветка, узлы, замечания по возвращённым задачам. Отдать Максиму для запуска.

**Утро:**
1. Собрать ночные PR и статусы CI.
2. Ревью по §2 этого файла. Визуал — скриншоты из артефактов CI против `design/figma/<узел>/screenshot.png`. Живой вызов MCP — только в спорных местах.
3. Мерж по порядку зависимостей. Утверждение эталонов из артефактов CI.
4. Вернуть задачу с замечаниями — замечания попадают в текст задания следующей ночи.
